# Roadmap: ศึกษาพฤติกรรม Bluetooth และเก็บล็อกด้วย ESP32

อัปเดตอุปกรณ์เป้าหมายเมื่อ 27 พฤศจิกายน 2026

**เป้าหมาย** ศึกษาว่า ESP32 ตรวจพบ Bluetooth จากอุปกรณ์เป้าหมายในสถานะใด เก็บข้อมูลดิบเพื่ออธิบายพฤติกรรม และตรวจสอบว่าผลรับมาจากเครื่องเป้าหมายอย่างไร จากนั้นค่อยขยายไปหูฟัง นาฬิกา และอุปกรณ์อื่น

อ่าน [ขอบเขตวิจัยปัจจุบัน](../docs/CURRENT_RESEARCH_SCOPE.md) ประกอบ แผน LoRa Mesh เดิมถูกเก็บไว้ที่ [Roadmap เดิม](../archive_initial_research/project_roadmap_lora_legacy.md) ซึ่งรักษาเนื้อหาและการแก้ไขที่มีอยู่ก่อนปรับครั้งนี้ไว้

## ตอนนี้อยู่ตรงไหน

ชุดถัดไปใช้ Arduino Nano ESP32 ตัวเดิมกับ Redmi Pad Pro ใช้ [ผลนำร่อง 5 เงื่อนไขชุดที่ 1 จาก Honor X7b 5G](../experiments/reports/ble_pilot_01_honor_states.md) เป็นแนวทางจัดรอบและควบคุมพื้นหลัง ผลของ Redmi Pad Pro จะออกจากรอบทดลองชุดใหม่

| ขั้น | ทำอะไร | ผลงานก่อนผ่านขั้น | สถานะ |
| :--- | :--- | :--- | :--- |
| 1. กำหนดชุดทดลอง | ยืนยันบอร์ด รุ่นย่อยของแท็บเล็ต OS และเงื่อนไขควบคุม | รายการอุปกรณ์และตารางสถานะทดสอบ | Nano ESP32 + Redmi Pad Pro รอบันทึกรุ่นย่อย, OS และ core จริง |
| 2. เตรียมตัวเก็บล็อก | ตรวจ EXP-03 และปรับการบันทึกข้อมูล | firmware, วิธีบันทึกไฟล์ และล็อกทดสอบ | คอมไพล์ผ่าน และล็อกจริงยืนยันรับรายงาน/ถอด AD_DETAILS/หยุดตามเวลา; ยังไม่รับรองทุก AD หรือทุกอุปกรณ์ |
| 3. ทดลองแท็บเล็ต | เก็บทีละสถานะและทำซ้ำ | CSV ดิบ พร้อม metadata และบันทึกเหตุการณ์ | Pilot 01 ของ Honor ครบ 5 เงื่อนไข ส่วน Redmi Pad Pro รอเก็บข้อมูล |
| 4. ตรวจการระบุเครื่อง | เทียบพื้นหลังกับการเปิด–ปิด/นำเครื่องเข้า–ออก | หลักฐานเชื่อมโยงผลรับกับเครื่อง และกรณีที่ยังไม่แน่ใจ | ใช้รอบควบคุมของ Redmi Pad Pro เพื่อประเมินว่าแยกสัญญาณจากพื้นหลังได้เพียงใด |
| 5. ขยายและสรุป | ทดลองหูฟัง/นาฬิกาตามที่มี แล้วสรุปข้อจำกัด | ตารางตรวจพบตามอุปกรณ์และสถานะ พร้อมรายงาน | ขั้นต่อไปตามผลของแท็บเล็ต |

ยังไม่กำหนดวันส่งหรือระยะเวลารวม เพราะยังไม่ยืนยันชุดอุปกรณ์และเวลาที่อาจารย์ให้

## 1. กำหนดชุดทดลอง

- ยืนยันบอร์ดจริง: เอกสารเดิมระบุ Arduino Nano ESP32 / ESP32-S3 ซึ่งเริ่มได้ที่ BLE และไม่รองรับ Bluetooth Classic
- บันทึกเวอร์ชัน Arduino core/ไลบรารี รุ่นย่อยแท็บเล็ต เวอร์ชัน Android/HyperOS และการตั้งค่าฟีเจอร์ที่เกี่ยวข้อง
- เริ่มทีละเครื่อง ระยะคงที่ เช่น 1 เมตร ตำแหน่งและทิศวางเดิม จดอุปกรณ์ Bluetooth อื่นในพื้นที่
- แยก Passive Scan และ Active Scan เป็นคนละชุด ไม่เปลี่ยนค่ารับกลางรอบโดยไม่บันทึก

## 2. เตรียมตัวเก็บล็อก

ใช้บทเรียนจาก [EXP-03 เดิม](../experiments/firmware/exp03_ble_sniffer/exp03_ble_sniffer.ino) และเริ่มทดสอบด้วย [BLE Behavior Logger ใหม่](../experiments/firmware/ble_behavior_logger/README.md) ซึ่งเก็บ legacy GAP reports แยก Advertising/Scan Response โดยยังไม่ใช้ EXP-05 รวมเป้าหมายหรือหน้าเรดาร์เป็นหลักฐานแทนข้อมูลดิบ

ข้อมูลที่ต้องการในชุดใหม่:

- `session_id`, `trial_id`, `device_label`, `condition` และเวลาเริ่มทดลอง
- `timestamp_ms`, MAC, address type, RSSI ดิบ และข้อมูลชนิดรายงานที่ API เปิดให้เข้าถึง
- Advertising payload และ Scan Response แบบ hex แยกกัน หาก stack/API ที่เลือกให้ข้อมูลได้; ระบุข้อจำกัดเมื่อแยกไม่ได้
- ชื่อ Manufacturer Data และ Service UUID ที่อ่านได้ เก็บค่าดิบควบคู่การแปลความหมาย
- scan mode, interval/window, นโยบายกรองผลซ้ำ และเวลาเริ่ม–หยุดสแกน เก็บใน metadata หรือแถวเหตุการณ์
- heartbeat/สถานะตัวรับ เพื่อแยกช่วงเงียบออกจากบอร์ดหยุดทำงาน พร้อมบันทึก reset/USB หลุดเมื่อทราบ

ต้องตรวจไฟล์ที่บันทึกกลับมาอ่านได้ แยกข้อมูลจากข้อความสถานะ และไม่ตัดข้อมูลดิบเพราะพยายามรวม MAC หรือระบุยี่ห้อล่วงหน้า

## 3. ทดลอง Redmi Pad Pro

ข้อเสนอเริ่มต้น: สภาพละ 5–10 นาที ทำซ้ำอย่างน้อย 3 รอบ โดยบันทึกเวลารอหลังเปลี่ยนสถานะ ค่าเหล่านี้เป็นแผนตั้งต้น ปรับได้ตามผลนำร่อง ไม่ใช่การรับรองความเพียงพอทางสถิติ

| รหัสเงื่อนไข | สถานะ | สิ่งที่ต้องตรวจ |
| :--- | :--- | :--- |
| BACKGROUND | นำเครื่องเป้าหมายออกจากพื้นที่ | ผลรับจากอุปกรณ์พื้นหลัง |
| BT_OFF | ปิด Bluetooth บนเครื่องเป้าหมาย | เทียบกับสถานะเปิด และบันทึกวิธีปิด/การตั้งค่าสแกนเบื้องหลัง |
| BT_ON_HOME | เปิด Bluetooth อยู่หน้าโฮม | พบอะไรโดยไม่เปิดฟีเจอร์แชร์ |
| BT_SETTINGS | เปิดหน้าตั้งค่า Bluetooth | ผลรับเปลี่ยนจากหน้าโฮมหรือไม่ |
| SCREEN_LOCKED | ล็อกจอวางนิ่ง | ตรวจพบต่อเนื่องไหม และช่วงเงียบยาวเท่าไร |
| SHARING_ON | เปิด Quick Share หรือฟีเจอร์ของรุ่นนั้น | เปลี่ยนฟีเจอร์ทีละอย่าง แล้วเทียบกับสถานะก่อนหน้า |
| ACCESSORY_CONNECTED | เชื่อมต่อหูฟังหรือนาฬิกา หากมี | แยกผลรับของแท็บเล็ตกับอุปกรณ์เสริม พร้อมบันทึกทั้งสองเครื่อง |

เก็บเป็นไฟล์แยกรอบ พร้อม metadata ที่ระบุ `device_label=REDMI_PAD_PRO` และแยก trial ID ของแต่ละรอบ ก่อนทดสอบ `SHARING_ON` ให้ตรวจเมนูและโหมดมองเห็นจริงบนเครื่อง

## 4. ตรวจว่าผลรับเป็นเครื่องเป้าหมายอย่างไร

- เทียบพื้นหลัง แล้วเปิด–ปิดหรือย้ายเครื่องเข้า–ออกตามเวลาที่จดไว้ ทำซ้ำเพื่อตรวจความสัมพันธ์
- เก็บ MAC และ payload เดิมทั้งหมด อย่าเพิ่งถือว่า MAC หนึ่งเท่ากับอุปกรณ์หนึ่ง
- แยกสิ่งที่ยืนยันได้ สิ่งที่คาดว่าใช่ และสิ่งที่ยังระบุไม่ได้ พร้อมเหตุผล
- รายงานเวลาจนตรวจพบครั้งแรก จำนวนผลรับต่อช่วงเวลา ช่วงห่างต่อ address/สตรีม RSSI และการเปลี่ยน payload/MAC
- ช่วงห่างที่ตัวรับเห็นไม่ใช่ advertising interval จริงโดยอัตโนมัติ และไม่มีจำนวนส่งอ้างอิงจึงยังคำนวณ packet loss ไม่ได้
- หากไม่พบ ให้รายงานว่าไม่พบภายในระยะเวลาและเงื่อนไขนี้ ไม่สรุปว่าเครื่องไม่มีสัญญาณ Bluetooth

## 5. ขยายอุปกรณ์และส่งมอบผล

เมื่อวิธีเก็บข้อมูลแท็บเล็ตใช้ซ้ำได้ จึงเลือกหูฟังและนาฬิกาที่มีมาทดสอบ เช่น เปิด/ปิด โหมดจับคู่ ยังไม่เชื่อมต่อ และเชื่อมต่อแล้ว สำหรับหูฟังที่มีเคสให้แยกปิดเคส/เปิดเคสตามรุ่น

ผลส่งมอบคือ firmware ตัวเก็บล็อกพร้อมวิธีใช้, CSV ดิบกับ metadata, ตารางตรวจพบตามสถานะ และรายงานข้อจำกัด ไม่ตั้งเป้าว่าต้องตรวจพบทุกเครื่อง

LoRa Mesh, Wi-Fi/BLE fusion, การคำนวณระยะแม่นยำ การหาทิศทาง และระบบกู้ภัยครบวงจร ยังไม่ใช่รายการส่งมอบระยะนี้ การขยายไป Bluetooth Classic ต้องพิจารณาฮาร์ดแวร์และวิธีทดลองแยกต่างหาก

## งานถัดไปที่ทำได้ทันที

1. จดรุ่นย่อยและเวอร์ชัน Android/HyperOS ของ Redmi Pad Pro, core/IDE ที่ใช้ และค่าระยะ/ความสูง/ทิศวางจริงใน metadata
2. เริ่ม Passive Scan รอบ `BACKGROUND`, `BT_OFF` และ `BT_ON_HOME` แล้วเทียบ MAC กับ payload จากแต่ละรอบ
3. ตรวจว่าแท็บเล็ตมี Quick Share โหมดรับหรือฟีเจอร์แชร์ใดให้ทดสอบ แล้วจึงเก็บเงื่อนไขแชร์/ล็อกจอซ้ำตามแผน บันทึกฟีเจอร์และการตั้งค่าที่ใช้จริง
