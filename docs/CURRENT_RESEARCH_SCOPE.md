# เป้าหมายปัจจุบัน: ศึกษาพฤติกรรม Bluetooth ด้วย ESP32

อัปเดต: 17 พฤศจิกายน 2026 ตามคำแนะนำอาจารย์ที่ผู้ทำโครงการแจ้ง

ศึกษาว่า ESP32 ตรวจพบสัญญาณ Bluetooth จากอุปกรณ์ได้ในสถานะใด และจะเชื่อมโยงผลรับกับอุปกรณ์เป้าหมายในการทดลองได้อย่างไร โดยเก็บล็อกจากโทรศัพท์ก่อน แล้วจึงขยายไปหูฟัง นาฬิกา และอุปกรณ์อื่นตามผลและอุปกรณ์ที่มี

แผนปฏิบัติงานหลักอยู่ที่ [Project Roadmap](../process_and_workflow/project_roadmap.md) เอกสารนี้กำหนดขอบเขตและใช้ตัดสินเมื่อเอกสารเก่าให้ทิศทางต่างกัน

## คำถามวิจัยที่ต้องตอบ

1. โทรศัพท์เปิด Bluetooth ในแต่ละสถานะแล้ว ESP32 ตรวจพบ BLE Advertising (ข้อความประกาศตัว) หรือไม่?
2. สิ่งที่รับได้เปลี่ยนอย่างไรเมื่อเปิดหน้าตั้งค่า ล็อกจอ เปิดแชร์ใกล้เคียง หรือเชื่อมต่ออุปกรณ์?
3. ต้องรอนานเท่าไรจึงพบครั้งแรก และมีช่วงเงียบระหว่างผลรับนานเพียงใด?
4. ผลรับใดมีหลักฐานว่ามาจากเครื่องเป้าหมาย และผลใดยังแยกจากสัญญาณพื้นหลังไม่ได้?
5. MAC และ payload เปลี่ยนอย่างไร และข้อจำกัดนี้กระทบการติดตามเครื่องเดิมอย่างไร?

การตรวจพบสัญญาณ การระบุว่าเป็นเครื่องใด และการหาตำแหน่ง เป็นคนละปัญหา ระยะนี้เน้นสองเรื่องแรก ไม่ตั้งสมมติฐานว่าทุกอุปกรณ์ต้องตรวจพบได้

## ขอบเขตและข้อจำกัด

- ใช้ ESP32 เก็บข้อมูลผ่าน USB Serial ลงคอมพิวเตอร์ เริ่มจาก BLE ตามความสามารถบอร์ดเดิม
- ต้องยืนยันรุ่นบอร์ดจริง เวอร์ชัน Arduino core/ไลบรารี และรุ่น/OS ของโทรศัพท์ก่อนเริ่มชุดข้อมูลใหม่
- บอร์ดเดิมที่เอกสารระบุคือ Nano ESP32 / ESP32-S3 ซึ่งรองรับ BLE แต่ไม่รองรับ Bluetooth Classic การศึกษาหูฟังจึงเริ่มได้เฉพาะสัญญาณ BLE ที่มันปล่อย ไม่ใช่การดักข้อมูลเสียงหรือการเชื่อมต่อ Classic ทั้งหมด
- แยก Passive Scan (รับฟัง) และ Active Scan (ส่งคำขอข้อมูลเพิ่มเติม) เป็นคนละเงื่อนไข
- การสแกนด้วย BLE stack ให้ผลรายงานที่ตัวรับเห็น ไม่ใช่การบันทึกทุกแพ็กเก็ต Bluetooth บนอากาศ
- เปิด Bluetooth แล้วอาจไม่พบ Advertising ในช่วงที่วัด ต้องรายงานรุ่น สถานะ เวลาสังเกต และการตั้งค่ารับประกอบ
- MAC หรือชื่อที่เปลี่ยนไม่พิสูจน์ว่าเป็นเครื่องใหม่ และหลาย MAC ไม่พิสูจน์ว่าเป็นหลายเครื่อง เก็บดิบก่อนรวมเป้าหมาย
- Manufacturer ID หรือ Service UUID เป็นเบาะแส ไม่ใช่หลักฐานยืนยันฟีเจอร์ รุ่น หรือเจ้าของเครื่องโดยลำพัง
- RSSI เป็นความแรงที่ตัวรับวัดได้ ยังไม่ใช้ยืนยันระยะจริงหรือทิศทาง

LoRa Mesh, Wi-Fi/BLE fusion, เรดาร์หาทิศทาง, multilateration และระบบกู้ภัยครบวงจรอยู่นอกแผนส่งมอบระยะนี้ เก็บเป็นประวัติหรือทางเลือกในอนาคต ไม่ใช่งานบังคับของแผนปัจจุบัน

## สถานะที่ยืนยันได้จาก Repo

- มี firmware BLE เดิม `EXP-03` และ CSV เดิม ใช้เป็นจุดเริ่มต้นและข้อมูลอ้างอิง
- ยังไม่มีหลักฐานว่าตัวเก็บล็อกเดิมผ่านข้อกำหนดแผนใหม่ครบแล้ว ต้องตรวจและปรับก่อนเก็บข้อมูลใหม่
- EXP-03 ใช้ Active Scan, ยังไม่เก็บ payload ดิบครบ และ `delta_t_ms` เป็นช่วงระหว่าง callback ทุกอุปกรณ์รวมกัน ไม่ใช่คาบของเครื่องเป้าหมาย
- ตัวเลขผลรับไม่ใช่จำนวนส่งจริงของเครื่อง จึงยังคำนวณ packet loss หรือยืนยันรับครบ 100% ไม่ได้หากไม่มีตัวอ้างอิงฝั่งส่ง
- ผลทดลองเก่าเป็นผลเฉพาะเงื่อนไขเดิม ไม่ใช้ยืนยันว่ามือถือทุกเครื่องหรือทุก OS มีพฤติกรรมเหมือนกัน
